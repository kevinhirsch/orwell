## PERSIST-1 [Severity: Blocker] [Effort: <1day] [Value: High]
Mid-process embedder degradation silently mixes two incompatible vector spaces inside the SAME per-houseguest recall index — cosine similarity becomes meaningless, with no error, no log, no test surfaced.

- **Where:**
  - `src/adapters/embedding/FastembedEmbedding.ts:64-74` — `embed()` catches ANY failure (worker timeout/crash) and permanently flips `this.degraded = true`, from then on returning `this.fallback.embed(text)` (the `DeterministicEmbedding`, **256-dim**) from the SAME long-lived provider instance every `SoulStore` shares (it's the one `runtimeEmbedding` singleton, `src/composition/engineRoot.ts:45-48`). The real fastembed model (BGE-small) is **384-dim**.
  - `src/adapters/inmemory/InMemoryVectorIndex.ts:23-29` — `cosine()` computes `Math.min(a.length, b.length)` and iterates that many dims. It **never validates the two vectors are the same length**. So after a mid-season degrade, a query embedded in the new 256-dim space against an item stored in the old 384-dim space (or vice versa) doesn't throw — it silently returns a truncated, semantically meaningless dot product as if it were a real similarity score.
  - `src/adapters/sqlite/SqliteVectorIndex.ts:53-63,82-92` — in `ORWELL_STORE=sqlite` mode the failure mode is different but equally silent: `ensureTable(dim)` locks the `vec0` table's column width at the FIRST insert (384, from fastembed). A later 256-dim insert (post-degrade) is **rejected by sqlite-vec** and `upsert()` throws — which lands in…
  - `src/adapters/engine/SoulStore.ts:130-138` (`indexOne`) — `try { … } catch { /* … */ }` — the catch body is a **comment, no logging at all**. From the moment of degrade onward, in SQLite mode, EVERY new memory for EVERY houseguest silently fails to index — recall freezes at the pre-degrade state for the rest of the process's life, invisibly.
- **Problem:** `engineRoot.ts`'s own doc comment states the load-bearing invariant explicitly: *"Vector SPACES must never mix inside an index → the provider is chosen ONCE per process lifetime… mixing vector spaces inside an index breaks cosine recall."* The runtime failure path directly violates that invariant the instant a worker dies/times out mid-season (plausible over a multi-day live game — the worker can crash for any transient reason), and nothing detects or prevents it. This directly answers the audit's "does semantic recall actually engage on deploy, and if it silently falls back does memory thin" question: recall doesn't just fall back cleanly, it can go **quietly wrong** (in-memory mode — worst case, since it never even errors) or **quietly frozen** (sqlite mode). This is exactly the kind of failure I5 ("nothing thins", "recalled in full") and I7 (behavioral fidelity grounded in real recall) is written to prevent, and it is invisible to every existing test (the deterministic test embedder never degrades mid-run) and to the operator (`/health`, see PERSIST-5).
- **Fix:** (1) In both `VectorIndex` implementations, capture the dimension on first `upsert` and **reject/log loudly** on any later vector of a different length instead of silently truncating (`InMemoryVectorIndex`) or swallowing the sqlite exception uncaught anywhere (`SoulStore.indexOne`, see PERSIST-6 for the trivial log fix). (2) On the FIRST `degraded` flip, have `SoulStore` (or the registry) mark every currently-resident sandbox's index as needing a full rebuild — since `rebuildSoulIndex()` already exists and runs on every `restore()`, the practical fix is to force an in-place `rebuildSoulIndex()` call (against the now-fallback embedder) for every resident sandbox the instant degrade fires, so the whole index moves to ONE consistent space rather than silently forking into two.

## PERSIST-2 [Severity: Major] [Effort: <1hr] [Value: High]
The shared `clamp01`/`clamp` helper has no NaN/Infinity guard — the systemic root cause that lets any single upstream division-by-zero or empty-array-average bug anywhere in the relationship/emotional pipeline silently turn a `number` field into a permanently-persisted `null`.

- **Where:** `src/engine/relationshipConstants.ts:141` — `export const clamp01 = (v: number): number => Math.max(0, Math.min(1, v));` and the duplicate at `src/domain/temperatureConstants.ts:77`. Both are called on every relationship-edge fold (`src/engine/relationships.ts:161-166,233,280`) and every emotional-state swing (`temperatureConstants.ts:105`).
- **Problem:** `Math.max`/`Math.min` propagate `NaN` unchanged (`Math.min(1, NaN) === NaN`), so `clamp01(NaN)` returns `NaN`. A relationship edge (`EdgeRecord.trust`/`affinity`/`threat`/`alignment`/`confidence`/`reliability`, all typed as non-optional `number`) or a soul's `emotionalState` that ever receives `NaN` from an upstream computation (e.g. a mean/ratio over an empty or degenerate set — several such expressions exist, e.g. `relationships.ts:233`'s `(meanAff - baseline) / (1 - baseline)`) will carry `NaN` in memory, and then **at the very next snapshot export**, `cloneSession`/`fastClone` — both explicitly documented to mirror `JSON.stringify` semantics (`sessionSnapshot.ts:372`: *"non-finite number becomes `null`"*) — silently rewrite that field to `null` in the durable save. This is a **type-contract violation baked permanently into the save file**: the field is declared `number` everywhere downstream but is now `null` on disk, forever (nothing in the save pipeline — `FileSaveStore`, `SqliteSaveStore`, or the 0031 checkpoint — validates numeric ranges or rejects a `null` where a `number` is contracted). This is the general mechanism behind the "NaN-into-the-permanent-layer write" another lane already flagged at a specific call site; fixing only that one call site leaves every other caller of `clamp01`/`clamp` (a dozen+ sites across `relationships.ts`, `temperatureConstants.ts`, `competitionOutcome.ts`) equally exposed to the same class of silent corruption.
- **Fix:** Add `if (!Number.isFinite(v)) return <safe fallback — e.g. the pre-clamp baseline, or 0/0.5 as appropriate>;` inside `clamp01` (and its sibling `clamp`/`clampSigned` variants if any exist) in BOTH locations — ideally consolidate the duplicate into one shared utility so there's only one place to guard. This is a one-line, near-zero-risk fix that closes the entire class of bug at its root rather than patching individual call sites as they're discovered.

## PERSIST-3 [Severity: Major] [Effort: <1hr] [Value: Med]
`RelationshipModel.load()` restores every edge field verbatim with zero validation — an already-corrupted `null`/NaN sitting in an existing save (from PERSIST-2's bug, or any future one) is never detected, repaired, or even logged on resume; it just keeps propagating.

- **Where:** `src/engine/relationships.ts:297-305` — `load()` does `this.edges.set(this.key(e.from, e.to), { trust: e.trust, affinity: e.affinity, threat: e.threat, alignment: e.alignment, confidence: e.confidence, reliability: e.reliability ?? … })` — a direct pass-through with no `Number.isFinite` check on any field.
- **Problem:** Fixing PERSIST-2 stops NEW corruption but does nothing for saves that already have a `null` trust/affinity/etc. On restore, `e.trust` becomes literally `null` (not `0`, not `undefined` — `null`, since that's what JSON round-tripped a `NaN`). Every downstream read of that edge (`edge(a,b).trust`, arithmetic like `null + delta`) coerces `null → 0` in JS numeric contexts, which is a **silent, undocumented, unannounced reset of that specific relationship edge to its floor value** every time the save is loaded — indistinguishable from a real (intentional) trust-0 relationship, and never surfaced to an operator via a log or a fault.
- **Fix:** In `load()`, sanitize each field with `Number.isFinite(e.trust) ? e.trust : this.constants.baseline.trust` (mirroring the existing `reliability ?? baseline.reliability` pattern already on the next line) for every numeric field, and `console.error` once per repaired edge so a corrupted save is at least visible in the logs instead of silently self-healing to a wrong value.

## PERSIST-4 [Severity: Major] [Effort: <1day] [Value: High]
Boot-time race: a sandbox built while the fastembed model is still warming up gets PERMANENTLY wired to the deterministic fake embedder for the rest of that sandbox's in-memory life, even after the real model finishes warming up moments later.

- **Where:** `src/composition/engineRoot.ts:50-69` (`buildEngineCore`) — `const embedding = runtimeEmbedding ?? new DeterministicEmbedding();` then `new SoulStore((text) => embedding.embed(text))`. This reads the module-level `runtimeEmbedding` **once**, at the moment `buildEngineCore()` is called, and closes over the resolved value — it never re-checks `runtimeEmbedding` again for that instance's lifetime. `src/main.ts:50,67-68` binds the HTTP server (`startHttpMcp`) — which wires `runtime.registry.resolver()`, and thus `sandboxFor()` → `buildEngineCore()` for any new/not-yet-resident user — **before** the `if (embedMode === "fastembed")` block (`main.ts:84-114`) awaits the warm-up (up to `ORWELL_EMBED_WARMUP_MS`, default 45000ms) and calls `setRuntimeEmbedding(provider)`.
- **Problem:** `deferResume` (per the comments at `runtime.ts:41-46,55-57`) only delays the BULK preload of already-known users — it does nothing to stop a live incoming HTTP request (a new user's `createCharacter`, or any request from a user not yet resident) from hitting the resolver and building a fresh sandbox during that up-to-45-second window. Every such sandbox's `SoulStore` is permanently bound to the 256-dim `DeterministicEmbedding`, never to be upgraded even after fastembed comes online seconds later — the ONLY way that sandbox's souls ever get real semantic recall is if it's later evicted (LRU idle-unload, `registry.ts:647-662`) and resumed (which rebuilds via `buildEngineCore()` again, this time correctly picking up the now-set `runtimeEmbedding`). A user who starts casting in the first 45 seconds after every engine restart/deploy silently gets degraded recall for their entire active session, with the boot log ultimately claiming `"[orwell] semantic recall: fastembed"` — a false signal for that specific sandbox.
- **Fix:** Make the embed closure a **live indirection** instead of a captured value: `new SoulStore((text) => (runtimeEmbedding ?? fallbackSingleton).embed(text))` — reading the module variable fresh on every call rather than snapshotting it at construction time. This is a small, surgical change (remove the `const embedding = …` binding, reference `runtimeEmbedding` directly inside the arrow function) that closes the race without touching the prod-incident-motivated boot ordering.

## PERSIST-5 [Severity: Major] [Effort: <1hr] [Value: High]
`/health`'s embeddings status is a one-time boot-time snapshot, not a live read — a fastembed worker that degrades mid-process (PERSIST-1's trigger condition) is never reflected there, so an operator watching Health & Logs sees "fastembed: healthy" forever even after recall has silently fallen back.

- **Where:** `src/main.ts:44-45` — `let embeddingsState: {…} = {provider:"deterministic", degraded:false}; const embeddingsStatus = (): {…} => embeddingsState;` and `:102-104` — `embeddingsState = provider.degraded ? {…} : {provider:"fastembed", degraded:false};` — this assignment runs **exactly once**, immediately after a successful warm-up (at which point `provider.degraded` is definitionally `false`, since degrade only happens on a LATER failed `embed()` call). Nothing ever re-reads `provider.degraded` after this point.
- **Problem:** `FastembedEmbedding.degraded` (the live flag, flipped inside `embed()` at `FastembedEmbedding.ts:67`) is never consulted again by `main.ts` after the initial assignment. The admin `/health` surface (and whatever FE card reads it, per CLAUDE.md's "Health & Logs card") is therefore **structurally incapable of ever reporting a mid-process degrade** — the exact failure PERSIST-1 depends on going undetected. This is a G1-tier observability gap on a feature CLAUDE.md explicitly calls out as "the embeddings-provider status surfaced on /health."
- **Fix:** Change `embeddingsStatus` to `() => provider ? { provider: provider.degraded ? "deterministic" : "fastembed", degraded: provider.degraded } : embeddingsState` (i.e., read the live flag off the retained `provider` reference every call) instead of caching a point-in-time value.

## PERSIST-6 [Severity: Minor] [Effort: <1hr] [Value: High]
`SoulStore.indexOne`'s catch block is completely silent — not even a `console.error` — so the ONE case that does throw today (a `VectorIndex.upsert` failure, e.g. the sqlite-vec dimension-mismatch reject in PERSIST-1) produces zero operator-visible signal.

- **Where:** `src/adapters/engine/SoulStore.ts:130-138`:
  ```ts
  private indexOne(hg: EntityId, mem: Memory): void {
    try {
      this.indexFor(hg).upsert(mem.id, this.embed(mem.content), { content: mem.content });
    } catch {
      // Vectors are derived state: a failed embed only degrades recall for this memory
      // (a restart re-derives every index); it must never crash the drain loop.
    }
  }
  ```
- **Problem:** The comment correctly argues the failure must not crash the drain loop — but "must not crash" and "must not log" are different requirements, and only the first is honored. Every other fault path in this codebase (the orchestrator's `logFaults`, the embedding warm-up failures in `main.ts`, `FastembedEmbedding`'s own degrade path) logs loudly per the CLAUDE.md mandate to "surface a fault where an operator can see it." This is the one silent exception, and it sits exactly on the path that would otherwise be the FIRST observable symptom of PERSIST-1.
- **Fix:** Add a single `console.error(\`[orwell] soul index upsert failed for ${hg}: ${e instanceof Error ? e.message : String(e)}\`)` in the catch. Trivial, zero risk, immediately actionable — this is the highest value-per-effort fix in this lane.

## PERSIST-7 [Severity: Major] [Effort: <1hr] [Value: Med]
`ORWELL_STORE=sqlite`'s vector index is always in-memory (`:memory:`) — the factory that's supposed to back it with durable sqlite-vec storage is called with no path argument, so opting into "the SQLite tier" doesn't actually persist embeddings, defeating the feature's stated purpose.

- **Where:** `src/composition/engineRoot.ts:63-64`:
  ```ts
  const makeIndex: (() => VectorIndex) | undefined =
    (process.env.ORWELL_STORE ?? "").trim().toLowerCase() === "sqlite" ? sqliteVectorIndexFactory() : undefined;
  ```
  vs. `src/adapters/sqlite/SqliteVectorIndex.ts:111-114`: `export function sqliteVectorIndexFactory(dbPath = ":memory:"): () => VectorIndex { const db = openVecDatabase(dbPath); … }`. Compare `SqliteSaveStore.ts:52-56`, which correctly derives its path from `ORWELL_DATA_DIR` (`${dataDir}/orwell.sqlite`).
- **Problem:** CLAUDE.md documents `ORWELL_STORE=sqlite` as "the built SQLite (`better-sqlite3`) + sqlite-vec save store" — a reasonable reading is that opting in makes the WHOLE relational tier (saves + vectors) durable. In practice only `SqliteSaveStore` gets a real on-disk path; the vector index factory call omits `dbPath` entirely and silently falls back to its own default (`:memory:`), so the embeddings vanish on every process restart regardless of `ORWELL_STORE`. Because `rebuildSoulIndex()` unconditionally re-derives every vector from the persisted `soul.memory` text on every `restore()`, this is **not** an I5 data-loss bug (no information is lost — the source-of-truth text is intact) but it IS a **silent feature gap**: the whole point of choosing sqlite-vec over the in-memory index (avoiding a full O(events) re-embed replay on every restart, and letting the vector store itself survive independently) is never realized, and a late-season restart under `ORWELL_STORE=sqlite` pays the exact same full-replay cost as the plain in-memory default — with no indication anywhere that the "durable" mode isn't actually durable for this piece.
- **Fix:** Thread a `dbPath` through, e.g. `sqliteVectorIndexFactory(\`${dataDir}/orwell.sqlite\`)` (sharing the same file as `SqliteSaveStore`, or a sibling `orwell-vec.sqlite`), consistent with how `SqliteSaveStore` derives its own path from `ORWELL_DATA_DIR`.

## PERSIST-8 [Severity: Major] [Effort: multi-day] [Value: High]
The 0031 fail-closed integrity checkpoint — the ONE mechanism enforcing "nothing persisted may ever be dropped" (mandate #4 / I5) — only verifies `events`, `knowledge`, `relationships` (presence only), `souls` (memory/history/beliefs), `characters` (byte-stable), `suspicions`, `vaultIds`, and `worldSnapshot`. It does **not** check roughly fifteen other SessionCore fields that features 0058 through 0107 added and whose own doc comments repeatedly promise "persisted so it survives a restart… accumulates, never thins (0007/0030)."

- **Where:** `src/engine/sessionSnapshot.ts:417-504` (`toGameState`, the ONLY projection the checkpoint ever compares) and `src/domain/saveState.ts:80-93` (`GameState` interface) / `:124-137` (`counts`/`DetailCounts`) / `:190-314` (`isSuperset`). Cross-reference the SessionCore fields these never touch: `deals` (0039), `alliances` (0107), `campaigns`/`campaignTickCount` (0085), `drives` (0086), `trajectories`/`trajectoryFolds`/`readAnchors` (0087/0088), `presence`/`presenceBase`/`presenceTenure`/`presenceZone`/`trackedSightings` (0049/0077/L21/L24), `deepProfiles`/`storyThreads`/`nominationWeeks`/`surfacedThreadCount` (0058/0060), `eruptionCount`/`triggerTickCount` (0091), `pacingDripWeek`/`pacingDripCount`/`pacingTickCount`/`pacingLastDrippedWeek` (0092), `confideState`/`confideLieCount` (0075), `secretUsedAs`/`secretExposeCount`/`secretTradeCount`/`secretPlayerBluffCount`/`secretPlayerBluffBelief` (0093/0099), `seededRelationships`/`playerTieSurfaceCount`/`surfacedTieSubjects`/`tieScheduleTickCount` (0059), `privateOrientations` (0063), `textureOverrides` (0070) — all defined in `sessionSnapshot.ts:38-329` and all restored by `GameSessionAdapter.restore()`, but NONE of them flow into `toGameState`'s `GameState` shape, so `counts()`/`isSuperset()`/`countsNonDecreasing()` are structurally blind to them.
- **Problem:** This is the single biggest coverage gap in the persistence stack relative to what the codebase itself claims to guarantee. If any bug in ANY of these dozen-plus subsystems — a botched migration, a mis-scoped `replaceHidden`, an off-by-one in a scheduler's bookkeeping map, a future refactor that accidentally resets a `Map` instead of merging it — silently drops or shrinks one of these fields between the checkpoint's `baseline` and `candidate` snapshots, the fail-closed 0031 gate (`Orchestrator.checkpoint`, `orchestrator.ts:392-447`) will see it as a clean, non-degrading commit and **persist it anyway**. Every one of these features was built AFTER the checkpoint's `GameState` projection was last extended (worldSnapshot, 0062, is the most recent addition to `toGameState` — everything listed above post-dates it and was never wired in). This means the game's own headline non-degradation guarantee has been silently narrowing in relative coverage with every new feature batch even as the surface area of "detail that must never thin" has grown — the exact inversion of I5's intent.
- **Fix:** Extend `GameState`/`counts`/`isSuperset` to cover each dimension with the *matching* semantics already established for existing fields (append-only ⇒ prefix/id-presence check like events/knowledge; monotonic counters ⇒ non-decreasing; legitimately-mutating maps ⇒ presence-only like relationship edges; byte-stable artifacts ⇒ byte-compare like `characters`/`worldSnapshot`). This is real, multi-day design work (each field needs its own correct comparison rule, mirroring the care already visible in the existing `isSuperset`), but it is the highest-leverage single change available in this lane: it closes a gap across the ENTIRE recently-shipped feature surface (0058–0107) in one pass rather than one bug at a time.

## PERSIST-9 [Severity: Major] [Effort: <1day] [Value: High]
`idempotencyCache` is wiped on every `restore()` — and because the SAME restore path also runs on ordinary LRU sandbox eviction (not just crash/deploy), a plain idle-then-return user session can silently double-apply a mutating action if the client's retry logic refreshes `expectedBeatSeq` before resending.

- **Where:** `src/adapters/engine/GameSessionAdapter.ts:2267` (`this.idempotencyCache.clear();` inside `restore()`) is reached from THREE places: (a) `registry.ts:611` `importSnapshot` on a fresh boot/resume, (b) `registry.ts:728` `importSnapshot` inside `GameSessionRegistry.restore()` — the orchestrator's checkpoint-fault rollback path, AND (c), critically, the **normal LRU idle-unload-then-resume cycle** (`registry.ts:647-662` saves + drops a sandbox past `maxResident`; the user's next request rebuilds via `sandboxFor` → the same `importSnapshot`/`restore()`). The idempotency check itself lives at `advanceGame` (`:5612-5626`) and `submitDecision` (`:5669-5684`): `if (req.idempotencyKey !== undefined) { const cached = this.idempotencyCache.get(req.idempotencyKey); if (cached) return cached; }` — **checked before** `guardBeatSeq`, and the comment at `:5613-5616` explicitly says the cache "WINS even if beatSeq has since moved."
- **Problem:** The persisted, restart-safe replay guard is `beatSeq` (Part A); the idempotency cache (Part B) is the ONLY thing that prevents re-EXECUTION of an already-applied mutation when a retry's `expectedBeatSeq` happens to still be valid against the CURRENT board. That happens whenever a client, on retrying a request it never got a response for, first re-reads game state (a completely reasonable, arguably *recommended* retry pattern) and resends the action with the freshly-observed `beatSeq` — at that point `guardBeatSeq` passes (the board legitimately advanced from the lost-response commit, and the fresh value matches), the idempotency cache MISSES (cleared by the intervening restore), and the mutation is **re-applied**: a vote gets cast twice, a `comp-intent` gets submitted twice, a nomination gets confirmed twice — whatever the action was, silently, with no error surfaced anywhere (I2/I10's "the game is fair and reproducible" and I4's "an action narrated but never recorded" both have an inverse failure mode here: an action recorded/folded TWICE). This is not a rare crash-only scenario — 64 resident sandboxes is the default cap (`GameSessionRegistry.DEFAULT_MAX_RESIDENT`), so on any deployment with more than 64 concurrently-touched users, a normal idle gap is enough to trigger the eviction-then-resume cycle that clears this cache.
- **Fix:** Persist a small, bounded (`IDEMPOTENCY_CACHE_MAX`-capped, already LRU-trimmed per `:834-839`) `idempotencyKey → AdvanceView` map inside `SessionCore` exactly like `beatSeq` is persisted — it's already bounded and already serializable (an `AdvanceView` is plain JSON), so the marginal snapshot-size cost is small and precedented by every other "small bookkeeping map" already carried on `SessionCore` (e.g. `pacingLastDrippedWeek`, `secretUsedAs`).

## PERSIST-10 [Severity: Medium] [Effort: <1hr] [Value: Med]
A corrupt notoriety file silently discards a user's entire cross-season reputation history with no quarantine, no backup, and no log — inconsistent with how every other durable store in this codebase treats corruption.

- **Where:** `src/adapters/engine/FileUserNotorietyStore.ts:44-52`:
  ```ts
  read(user: string): NotorietySummary | null {
    const file = this.fileFor(user);
    if (!existsSync(file)) return null;
    try {
      return JSON.parse(readFileSync(file, "utf8")) as NotorietySummary;
    } catch {
      return null; // a corrupt notoriety file is non-fatal — the user simply reads as un-known this season
    }
  }
  ```
  `accumulate()` (`:54-71`) then calls `accumulateNotoriety(this.read(user), summary)` — with `read` having just returned `null`, this treats the user as brand new and OVERWRITES the single on-disk file with just the current season's summary.
- **Problem:** `FileSaveStore.loadLatest` (`FileSaveStore.ts:179-190`) treats an unreadable save as a serious event: it QUARANTINES the bad file (renames to `.corrupt`, so it's recoverable and never silently mistaken for current) and steps down to an OLDER version rather than losing the data. `FileUserNotorietyStore` has no versioning at all (one file per user, no history), so a corrupt read has nowhere to step down to — and unlike `FileSaveStore` it doesn't even rename-and-preserve the bad file before overwriting it. Given CLAUDE.md's own framing of notoriety as "account-level reputation must survive the season cutover by construction" and monotonic accumulation being the entire point of the feature (0104), a silent full reset on ANY read hiccup (a torn write from an unrelated disk fault, a manual inspection tool that half-edits the file, a future refactor that changes the JSON shape without a migration) is a real, if narrow, non-degradation violation with zero operator visibility.
- **Fix:** On a parse failure, rename the bad file to `${file}.corrupt-${Date.now()}` (mirroring `FileSaveStore`'s pattern) BEFORE returning `null`, and `console.error` loudly — so the loss is at least detectable and the raw bytes are recoverable for forensic repair, instead of being silently clobbered by the very next `accumulate()` call.

## PERSIST-11 [Severity: Minor] [Effort: <1hr] [Value: Low]
`FileSaveStore.prune()`'s periodic-checkpoint math wastes one of its three retained checkpoint slots on a version that's already covered by the recent-retention window, whenever the checkpoint boundary falls close to `latest` — silently thinning the long-tail archive's actual depth for ~10% of all saves.

- **Where:** `src/adapters/engine/FileSaveStore.ts:110-125` (also duplicated in `SqliteSaveStore.ts:157-174`):
  ```ts
  private prune(dir: string, latest: number): void {
    const keep = new Set<number>();
    for (let v = latest; v > latest - FileSaveStore.RETAIN_RECENT && v > 0; v--) keep.add(v);
    let checkpoints = 0;
    for (let v = latest - (latest % FileSaveStore.CHECKPOINT_EVERY);
      v > 0 && checkpoints < FileSaveStore.RETAIN_CHECKPOINTS;
      v -= FileSaveStore.CHECKPOINT_EVERY) {
      keep.add(v);
      checkpoints++;
    }
    …
  }
  ```
- **Problem:** With `RETAIN_RECENT=5`, `CHECKPOINT_EVERY=50`, `RETAIN_CHECKPOINTS=3`: whenever `latest % 50 <= 4` (roughly 1 save in 10), the FIRST computed checkpoint version (`latest - (latest % 50)`) lands inside the already-kept recent-5 window (e.g. `latest=200` → first checkpoint candidate is `200` itself, already retained; `latest=201` → candidate `200`, still inside `197..201`). The loop still increments `checkpoints` for that redundant hit, so by the time it reaches versions genuinely OUTSIDE the recent window it only has 2 more iterations left, not 3 — the long-tail archive ends up with 2 distinct historical checkpoints instead of the intended 3 for roughly one save in ten. Not a data-loss bug (the CURRENT save is never at risk — this only affects how deep the periodic backup archive reaches), but a real, easily-fixed thinning of the deliberately-designed crash-recovery depth.
- **Fix:** Start the checkpoint scan strictly BELOW the recent-retention floor: `for (let v = Math.min(latest - CHECKPOINT_EVERY, latest - RETAIN_RECENT) - ((...) % CHECKPOINT_EVERY); …)` or simply skip a candidate that's already in `keep` without consuming a `checkpoints` slot (`if (keep.has(v)) continue;` before incrementing).

## PERSIST-12 [Severity: Polish] [Effort: <1hr] [Value: Low]
`InMemoryVaultStore.writeHidden` has no duplicate-id protection, unlike the `EventStore`'s explicit "fail loud on a duplicate id" contract — a latent inconsistency that would silently double-write if any future Vault-writing path ever imports the same record twice.

- **Where:** `src/adapters/inmemory/InMemoryVaultStore.ts:14-16` — `writeHidden(record) { this.records.push(record); }`, no id check. Compare `InMemoryEventStore.record()` (`InMemoryEventStore.ts:22-25`): `if (this.ids.has(event.id)) throw new Error(\`duplicate event id: ${event.id}\`);` — explicitly justified by the comment as protecting "the id-keyed superset checkpoint (0031)" from silent corruption.
- **Problem:** Today this is provably safe: every call site that restores Vault records (`registry.ts:412`, `for (const r of snap.vault ?? []) sb.engine.vault.writeHidden(r);`) only runs once per fresh `buildUserSandbox()` call (each restore path always constructs a brand-new sandbox first), so no current code path can double-import. But the asymmetry with `EventStore` — which treats a duplicate id as a serious, fail-loud bug specifically BECAUSE the 0031 checkpoint's `vaultIds` presence-check (`saveState.ts:258-259`) would otherwise be fooled by silently-duplicated ids inflating `vaultRecords` counts without adding real content — is an unguarded landmine for the next engineer who wires a Vault-writing seam that (unlike today's) could legitimately be called twice on a live sandbox (e.g. a retry-safe write-back).
- **Fix:** Add the same `if (this.records.some(r => r.id === record.id)) throw …` (or a `Set<string>` of seen ids, mirroring `InMemoryEventStore`) to `writeHidden`, for consistency and defense-in-depth — cheap now, expensive to diagnose later if a real double-write ever happens silently.

## PERSIST-13 [Severity: Minor] [Effort: <1hr] [Value: Med]
`restore()`'s deep-profile/story-thread re-derivation branch is gated by an OR of two fields that are always expected to co-occur — if a save ever has one without the other, the game silently loads an EMPTY hidden-secrets layer for every houseguest instead of re-deriving it deterministically.

- **Where:** `src/adapters/engine/GameSessionAdapter.ts:2352-2362`:
  ```ts
  if (core.deepProfiles || core.storyThreads) {
    this.deepProfiles = core.deepProfiles ? cloneSession(core.deepProfiles) : {};
    this.storyThreads = core.storyThreads ? cloneSession(core.storyThreads) : [];
  } else if (core.house && core.seed !== undefined) {
    const layer = generateCastDeepLayer(core.seed, core.house.npcs);
    this.deepProfiles = layer.hidden;
    this.storyThreads = layer.threads;
  } else {
    this.deepProfiles = {};
    this.storyThreads = [];
  }
  ```
- **Problem:** The intent is clearly "pre-0058 legacy save (neither field) ⇒ re-derive deterministically from the seed; 0058+ save ⇒ trust the persisted layer." But the guard is an OR over two INDEPENDENT optional fields, and the two branches inside the `if` don't cross-check each other: a save where `storyThreads` is present (non-empty, so the outer OR is true) but `deepProfiles` is absent/empty (e.g. from a partial write, an interrupted `setOnSealProfiles`, or a future migration bug that clears one but not the other) takes the "trust the persisted layer" branch and sets `this.deepProfiles = {}` — silently discarding EVERY houseguest's secrets/goals/weakness/day-one-perception for the rest of the game, with no re-derivation, no error, and no non-degradation check to catch it (this ties directly into PERSIST-8: `deepProfiles` is one of the fields the 0031 checkpoint never verifies at all). This is a severe potential loss (the entire hidden-personality layer that grounds NPC voice, per the 0041 "linchpin") gated behind an implicit coupling assumption that is never asserted or tested.
- **Fix:** Require BOTH fields (`if (core.deepProfiles && core.storyThreads)`) to trust the persisted layer, or — more robust — treat the two fields independently: re-derive `deepProfiles` from the seed whenever it's missing regardless of `storyThreads`'s presence, and vice versa, so a partial/inconsistent save self-heals deterministically instead of silently going empty.
