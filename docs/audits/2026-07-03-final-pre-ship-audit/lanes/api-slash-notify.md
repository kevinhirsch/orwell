## API CONTRACT

### [API-1] [Severity: Minor] [Effort: <1hr] [Value: Med]
Unguarded `int()` conversion on `/portrait/studio/finalize` crashes to a bare 500
- **Where:** `frontend/routes/orwell_routes.py:907-924` (`orwell_portrait_studio_finalize`)
- **Problem:** The route parses the JSON body defensively (`try/except` around `request.json()`), but the very next line is `p = orwell_portraits._candidate_path(user, int(index)) if index is not None else None` — `int(index)` is OUTSIDE any try/except. If `index` is present but not integer-coercible (e.g. a string like `"abc"`, `null` handled fine, but `"1.5"` or an object), Python raises an unhandled `ValueError`/`TypeError` and FastAPI returns a generic, uncaught 500 instead of the route's own established pattern (`400 {"error": "no such candidate — generate options first"}`) used two lines later for every OTHER invalid-index case. Every sibling route in this file (`/portrait/library/select`, `/casting/photo`, `/decision`) validates before touching engine/FS calls; this one doesn't. In normal FE flow `st.selected` is always a valid array index (see `orwellHeadshot.js:258-272`), so this is unreachable through the shipped UI, but it is a real gap against any other caller (a future FE bug, a directly-scripted request, or a fuzzer) and a missing-validation pattern the audit charter explicitly asks to flag.
- **Fix:** Wrap the `int(index)` conversion in the same try/except that already guards `request.json()` (or a dedicated `try: idx = int(index) except (TypeError, ValueError): return JSONResponse(400, ...)`), returning the existing 400 "no such candidate" shape.

### [API-2] [Severity: Major] [Effort: <1day] [Value: High]
The decision card's 409 recovery message is a lying control — nothing actually refreshes, and the card can wedge open indefinitely
- **Where:** `frontend/static/js/orwellDecision.js:653-714` (submit handler + 409 branch), `:822-854` (the rearm/backstop pollers)
- **Problem:** When `POST /api/orwell/decision` returns 409 (the board moved since the card armed — a real, expected race per `orwell_routes.py:1085-1099`), the catch block sets: `err.textContent = "The board moved since this card appeared — refreshing the latest state. Try again in a moment, or decide in conversation."` But no refresh is ever triggered from this path — `confirm.disabled` is simply re-enabled and the SAME stale options/selection remain on screen. Worse, the two self-healing seams that exist elsewhere in this file cannot rescue it: `rearmFromStatus()` only runs on boot/`orwell:gamechanged`, and the 2.5s backstop poll (`:830-854`) explicitly no-ops whenever `document.getElementById(CARD_ID)` already exists — which it does, because the failed card was never removed. So a genuinely stale decision card sits inert, telling the player a refresh is in progress that isn't happening, until the player notices and manually clicks the × to dismiss it (only then does the backstop poll get a chance to fetch the real, current pending and re-arm a fresh card). This is exactly the "dead/lying control" pattern the audit charter calls out, and it sits on the single most consequence-bearing surface in the game (binding eviction/nomination/jury decisions).
- **Fix:** On a 409, actively re-fetch `/api/orwell/status` and either (a) replace the card in place with the fresh `pending` (same id, updated options) if one exists, or (b) remove the stale card entirely so the 2.5s backstop poll can re-arm the real one — and only then show copy that claims a refresh happened.

### [API-3] Verified NOT a bug (recorded for completeness)
Portrait cache-busting — investigated, confirmed correctly handled
- **Where:** `frontend/src/orwell_portraits.py:419-460` (`portrait_ref`, per-cast "epoch" version)
- **Note:** `/api/orwell/portrait/{houseguest_id}` sets `Cache-Control: private, max-age=86400`, which looked like a stale-image risk on regeneration, but `portrait_ref()` mints a `?v=<epoch>` cache-busting query param that rotates on any cast change, so a re-shot face always gets a fresh URL. No action needed — listed only so a future auditor doesn't re-flag it.

### [API-4] [Severity: Minor] [Effort: <1hr] [Value: Low]
`/api/orwell/layout` PATCH doesn't reject an empty `windowId`
- **Where:** `frontend/routes/orwell_routes.py:1252-1287`
- **Problem:** `LayoutPatchRequest.windowId: str` has no `min_length`, so a caller (or a JS bug that sends `windowId: ""` before a window kit instance has assigned its real id) passes FastAPI's Pydantic validation and reaches `orwell_layout.patch_layout(user, "", body.state)`. This silently writes/persists a keyless (`""`) layout record per user rather than 400ing on an obviously-invalid id — junk state that then round-trips through the 0064 sync layer (GET /layout, `layout-changed` fan-out) to every device.
- **Fix:** Add `windowId: str = Field(min_length=1)` (or an explicit `if not body.windowId.strip(): return 400`) alongside the existing "no usable layout fields" 400 check.

### [API-5] [Severity: Polish] [Effort: <1hr] [Value: Low]
`/api/orwell/health`'s `busy` field type is inconsistently treated
- **Where:** `frontend/routes/orwell_routes.py:440-457` (`orwell_health`), `frontend/static/js/orwellEngineStatus.js:104`
- **Problem:** The route returns `"busy": detail.get("busy")` which is either the string `"creating"` or `None`/absent — but the doc comment for the route only says "`busy` while createCharacter is in flight" without specifying the contract is a sentinel STRING, not a boolean. The one FE consumer happens to test `d.busy === "creating"` correctly today, but nothing in the route's own response model documents/enforces that shape (no Pydantic response_model on any of these routes), so a future consumer coding to "`busy` is a bool" (a very natural assumption from the field name) would silently always read `truthy` for any non-null value — an easy contract break with no compiler/schema catch.
- **Fix:** Either rename the field to `busyReason: Optional[str]` (self-documenting) or add a lightweight Pydantic response model to `/health` so the shape is enforced/discoverable instead of implicit tribal knowledge.

## SLASH COMMANDS

### [SLASH-1] [Severity: Blocker] [Effort: <1day] [Value: High]
Full workspace session-CRUD (`/chats delete`, `delete all`, `truncate`) ships live under the game build and can permanently destroy the visible record of the player's ONE active season with no game-aware guardrail
- **Where:** `frontend/static/js/slashCommands.js:913-951` (`_cmdSessionDelete`), `:1007-1019` (`_cmdSessionTruncate`); backing route `frontend/routes/session_routes.py:564-606` (`DELETE /session/{sid}`); `GAME_SLASH_KEEP` at `slashCommands.js:5903-5908` includes the whole `'chats'` group with no per-subcommand carve-out
- **Problem:** CLAUDE.md's mandate #4 (non-degradation, "persisted detail must never be lost across saves") is framed around the engine's Vault/state layer, but from the PLAYER's actual experience the FE chat transcript IS the readable record of "the story so far" — narration, ceremony beats, everything they've read all season. `/chats delete` (no args = current session, i.e. potentially the canonical game session) fires an immediate DELETE with **no confirmation prompt at all** (contrast the GUI/new-season flows, which gate destructive actions behind `window.styledConfirm` — see `orwellNewSeason.js:152-158`, `:231-237`). `/chats delete all` / `/s rm -rf` bulk-deletes every non-starred (or, with `-rf`, every) session in one call. `/chats truncate N` permanently deletes all-but-the-last-N messages of the CURRENT session with a bare one-line usage-error as the only validation — no confirmation, no "this cannot be undone." All three are reachable in the game build today because the entire `chats` command GROUP is in `GAME_SLASH_KEEP` (the keep-set is coarse — per top-level command, not per subcommand), and `/help` even advertises `/chats delete`-family aliases as ordinary "Shortcuts." A player who reflexively types `/clear`, `/rm`, or a Big-Brother-flavored "wipe this and start clean" moment could nuke the one thing they came to reread. (Deleting the canonical session correctly unbinds it server-side per GAP-1's fix in `session_routes.py:583-592`, so it won't corrupt the mirror stream — but the transcript itself is gone, and the very next chat starts from zero narration context while the engine is deep in, say, week 5.)
- **Fix:** Either (a) drop `delete`, `delete all`/`-rf`, `truncate`, and `clear` from the game-build keep-set entirely (the roster/status/HUD surfaces plus `/diary-room` already cover legitimate in-game needs — there's no diegetic reason a houseguest needs `rm -rf` on their own memory), or (b) if any must stay, route them through the SAME `styledConfirm` gate the GUI destructive actions use, and refuse outright (with a clear message) when the target is the canonical game session.

### [SLASH-2] [Severity: Major] [Effort: <1day] [Value: High]
`/chats new` and `/chats switch` promise something the engine won't actually deliver once a game is live
- **Where:** `frontend/static/js/slashCommands.js:847-911` (`_cmdSessionNew`), `:1034-1046` (`_cmdSessionSwitch`); the redirect mechanism at `frontend/routes/chat_helpers.py:3395-3422` (`_resolve_canonical_session`)
- **Problem:** `_resolve_canonical_session` documents its own behavior plainly: for any FRAMED, STARTED-game turn, the run is ALWAYS persisted onto the canonical session id, regardless of which session_id the request came from, and the FE eventually converges the viewing tab onto that canonical session (`canonical_session` event → `selectSession`). Neither `_cmdSessionNew` nor `_cmdSessionSwitch` has any awareness of this — `_cmdSessionNew` happily reports "created" a brand-new named chat, and `_cmdSessionSwitch` happily reports "Switched to X", but the moment the player sends an in-character message from that "new"/"switched-to" session while a season is active, the reply gets written to the canonical session and the tab gets silently pulled back onto it. From the player's point of view they asked for (and were told they got) a separate scratch conversation, and instead either nothing they typed shows up where they expect it, or their view snaps back to the game mid-thought. (This is the same fragile seam that produced the documented #1086 regression — "a settle-time session switch that strips the just-streamed reply" — so the underlying mechanism is known-flaky; this finding is that the SLASH COMMAND surface has zero UX acknowledgment of it.)
- **Fix:** When a game is `started`, either block `/chats new`/`/chats switch` with an in-fiction refusal (mirroring the `GAME_SLASH_KEEP` refusal copy: "your season only has one broadcast — there's nowhere else to switch to"), or have the command itself warn that it will converge back onto the live game the moment the player writes anything in-character.

### [SLASH-3] [Severity: Minor] [Effort: <1hr] [Value: Med]
`/help` teaches zero in-fiction mechanics under the game build (corroborating detail for the known finding)
- **Where:** `frontend/static/js/slashCommands.js:5420-5463` (`_cmdHelp`)
- **Problem:** The prior audit already flagged that `/help` doesn't teach the game; this pass confirms the concrete gap: the categories iterated are strictly `['Getting started', 'Tours', 'Chats', 'Settings', 'Memory', 'Productivity', 'AI Tools']`, and even filtered to the game-build keep-set, the output is exclusively `/chats …`, `/theme`, `/settings`, `/find`, plus the closing "Shortcuts: /new /rename /fork /clear /export" line. There is no entry anywhere for the Diary Room, the cast roster, decision cards, self-eviction, or how a season actually plays — the ONE discoverability surface a confused new player would reach for (`/help`) teaches them how to manage chat sessions and nothing about being a houseguest.
- **Fix:** Add a `category: 'The House'` (or similar) block to `/help`'s game-build output covering the actual player-facing affordances: the Diary Room button, the Cast panel, how decision cards work, and that "just talk" is the core verb — sourced from the existing sidebar buttons/gadgets so it doesn't drift from what's actually shipped.

## NOTIFICATIONS

### [NOTIFY-1] [Severity: Major] [Effort: <1day] [Value: High]
The engine-status banner names raw internal tool identifiers to the player — a literal I9 violation
- **Where:** `frontend/static/js/orwellEngineStatus.js:111-115`; source data from `frontend/src/orwell_engine.py:877-882` (`engine_health_detail`, `lastError.tool`)
- **Problem:** When the engine is reachable but a recent tool call failed, the banner renders: `show("degraded", "Big Brother engine reported a problem.", (le.tool ? le.tool + ": " : "") + le.error)`. `le.tool` is literally the MCP tool's programmatic name as registered in the engine's tool surface (e.g. `recordInteraction`, `advanceGame`, `submitDecision`), and `le.error` is whatever string the engine's exception handling produced — potentially including exception class names or other internals. The comment at the top of the file frames this as "an honest, out-of-character signal," which is a defensible design intent, but the vision brief's I9 invariant is written without an OOC carve-out ("no engine/tool/app/system talk in ANYTHING the player sees") — an OOC banner is still something the player sees, and naming a tool by its internal identifier is exactly the kind of machinery leak the mandate exists to prevent (distinct from the OOC "glitch complaints never enter the FICTION" clause, which is about keeping complaints out of narration, not about what a banner may say). This is also the single MOST LIKELY notification a player will see during any real engine hiccup, since it's the honest-outage banner, not a rare edge case.
- **Fix:** Translate `le.tool` through a small human-readable map (e.g. `{"recordInteraction": "recording a scene", "advanceGame": "moving the week forward", "submitDecision": "locking in a decision"}`) before it reaches the banner, falling back to a generic "an action" for any unmapped tool — so the OOC signal stays honest and actionable without naming engine internals.

### [NOTIFY-2] [Severity: Minor] [Effort: <1day] [Value: Med]
The above-composer notice zone has no height ceiling — simultaneous notices can crowd out the composer on short viewports
- **Where:** `frontend/static/js/orwellNotice.js:149-153` (`#orwell-notice-zone` CSS)
- **Problem:** The zone is a plain `display:flex; flex-direction:column` column with `gap` and a `max-width`, but no `max-height`/`overflow-y`. Up to four affordance kinds can legitimately co-occupy this ONE zone simultaneously (`guide`, `system-notice`, `continue`, `decision` — the `toast` and `top-banner` kinds use separate anchors, so they don't compound this). A realistic case: week-1 premiere (`guide`, persistent until dismissed) + a `comp-intent` decision card (own inner content: prompt, stillIn list, three option chips, a note, possibly a risk badge) + a `continue` nudge, all at once, on a phone in landscape or with an on-screen keyboard eating vertical space. Nothing in this file (or its consumers) caps the stack's height or makes it independently scrollable, so worst case the composer itself gets pushed toward/off the bottom of the viewport — exactly the class of failure the charter asks to hunt across "every state × every breakpoint."
- **Fix:** Give `#orwell-notice-zone` a `max-height` (e.g. `40vh` or `min(40vh, 320px)`) with `overflow-y: auto` once more than ~2 cards are stacked, so the composer input never loses its guaranteed screen real estate regardless of how many affordances are simultaneously live.

### [NOTIFY-3] [Severity: Minor] [Effort: <1hr] [Value: Med]
Every toast (success/error/info) shares one singleton slot — a rapid second toast silently overwrites the first with no queue or history
- **Where:** `frontend/static/js/ui.js:245-261` (`_ensureToastNotice`, one shared `_toastNotice`), `:266-368` (`showToast`/`showError`); `frontend/static/js/orwellNotice.js:666-699` (`show()` — reuses the connected element in place)
- **Problem:** `showToast`/`showError` both call `_ensureToastNotice()`, which lazily creates and forever reuses ONE `OrwellNotice` instance (`id: 'orwell-toast'`). Calling either function again while a toast is still visible calls `n.update(...)` (which mutates the same DOM node's body/severity/title in place) then `n.show()` — there is no queue, so an in-flight message is instantly replaced, not appended or deferred. In an app with 88 call sites for `showToast` (per the file's own comment) across independent subsystems (copy-to-clipboard, portrait backfill, session archive, casting-photo status, etc.), it's entirely plausible for two unrelated actions to fire within the same second — e.g. a "Copied" success toast firing while a slower background "portraits/backfill" `showError`("The photo service is offline right now.") is still on screen (or vice-versa). Whichever fires second wins, and the first message is simply gone with no way to recover it (no toast history/log panel).
- **Fix:** At minimum, don't let a lower-severity/informational toast (`success`/`info`) silently replace a still-visible `error`/`warn` toast that hasn't reached its own auto-dismiss time — mirror the `#766` severity-precedence rule the top-banner already implements (`orwellNotice.js:109-115`, `SEVERITY_RANK`) for the toast host too.

### [NOTIFY-4] [Severity: Minor] [Effort: <1hr] [Value: Low]
`showError` toasts auto-dismiss after just 3000ms while carrying an assertive/alert role
- **Where:** `frontend/static/js/ui.js:360-368`
- **Problem:** `n.o.autoDismissMs = 3000;` for every error toast — 3 seconds is on the short end even for a sighted, attentive player to read and act on an error, and per NOTIFY-3 the same slot can be pre-empted even sooner by an unrelated toast. There's no user-controllable dismiss delay and no persistent record of what the error said once it's gone (no "recent notifications" surface anywhere in this kit).
- **Fix:** Extend error-severity auto-dismiss to something in the 5–8s range (matching the `showToast` action-toast default of 5000ms already used elsewhere in the same file), or make error toasts NOT auto-dismiss (dismissible only) since they're rarer and more consequential than success confirmations.

### [NOTIFY-5] [Severity: Polish] [Effort: <1hr] [Value: Low]
Swipe-to-dismiss and auto-dismiss bypass the `onDismiss` callback contract
- **Where:** `frontend/static/js/orwellNotice.js:611-624` (`_armAutoDismiss` calls `self.hide()`), `:649-657` (swipe `end()` calls `self.hide()`), vs. `:834-840` (`dismiss()` is the only path that invokes `this.o.onDismiss`)
- **Problem:** The kit's documented contract is `onDismiss(reason)` fired "after a dismiss ('user' | 'remote' | 'api')" — but that callback is wired only into `dismiss()`, which is invoked ONLY by the explicit × click handler (`:599`). Both the auto-dismiss timer and the touch swipe-to-dismiss gesture call `hide()` directly, which never touches `onDismiss`. Today's only toast consumer (`ui.js`) doesn't pass `onDismiss`, so this is latent rather than actively broken, but it's a real API inconsistency: any future consumer that wires an `onAction`/`onDismiss` pair (e.g. a genuine "Undo" toast, which the code comments repeatedly reference as the target use case — "Session archived… Undo") would find that a swipe-away or a timeout silently skips their cleanup/finalize logic, while a click on their own × (via the action-toast's bespoke close button, which ALSO calls `n.hide()` directly at `ui.js:343`) does too.
- **Fix:** Route `_armAutoDismiss`'s timeout and the swipe handler's `end()` through `dismiss('timeout')`/`dismiss('swipe')` instead of bare `hide()` (with `persistDismiss` already false for toasts, this costs nothing and closes the API gap).

### [NOTIFY-6] [Severity: Blocker] [Effort: <1day] [Value: High]
Exiting Diary Room mode leaves the confessional draft in the composer — the next Enter sends it to the house as an in-character message
- **Where:** `frontend/static/js/orwellDiaryRoom.js:144-152` (`exitDRMode`), `:165-208` (`wireComposer`, the capture-phase submit interceptor), `:205-207` (Escape handler); `frontend/static/js/orwellComposerDraft.js:159` (the only other `orwell:drmode` listener, which persists the draft but never clears it)
- **Problem:** The Diary Room's entire value proposition, stated in its own header pill, is "private & out-of-character; the house never hears this." `exitDRMode()` — triggered by Escape (`:205-207`) or the pill's × button (`:90-93`) — resets `drMode = false`, hides the pill, and restores the placeholder, but never touches `box.value`. The capture-phase submit interceptor at `:170` only intercepts when `if (!drMode) return;` — once `drMode` is false, ANY subsequent Enter/send falls straight through to the normal chat pipeline. The only other consumer of the `orwell:drmode` event, `orwellComposerDraft.js:159`, merely calls `saveNow()` (persists the draft + the mode flag together) — it does not clear the textarea on an exit either. Concretely: the player opens the Diary Room, types "I think Sam is coming after me next," realizes mid-sentence they'd rather say it differently, hits Escape to back out (a completely natural UI instinct — Escape is the universal "back out" key) — and their private strategic confession is now sitting in the main composer with the mode indicator gone, one Enter away from being narrated to the house as something their character said out loud. This directly and concretely breaks I3 (knowledge only through pathways) and I9's privacy guarantee, and it's the single highest-consequence bug found across all three territories in this audit: a mechanical failure that can leak the exact kind of secret information the whole Vault Wall exists to protect, from the player's own hand.
- **Fix:** `exitDRMode()` must clear (or at minimum prompt to keep-or-discard) `box.value` whenever it fires from Escape/× — the safest default is to clear it unconditionally (mirroring how a real Diary Room booth doesn't let you carry a half-said confession out into the living room), dispatching the `input` event so the composer-draft module's persisted state and the visible textarea agree.

### [NOTIFY-7] [Severity: Polish] [Effort: <1hr] [Value: Low]
Diary Room failure copy risks not re-announcing on a second consecutive identical failure
- **Where:** `frontend/static/js/orwellDiaryRoom.js:193-199`
- **Problem:** On a failed `submitDR`, the handler sets `pill.setAttribute("aria-live", "assertive")` and `pill.firstElementChild.textContent = "📔 The Diary Room camera glitched — try again."` If the player immediately retries (the `_drSubmitting` gate allows this) and the SAME failure recurs, `textContent` is set to the byte-identical string — some screen readers/browsers only fire an `aria-live` announcement on a DOM mutation, and setting identical text may not always register as one, so a second consecutive failure could go unannounced to an AT user even though the visible text hasn't changed (making it look unchanged rather than "confirmed still failing").
- **Fix:** Append a tick/counter or a zero-width variance to the message on a repeated identical failure (e.g. alternate a trailing space, or append "(still failing)" past the first retry) so the mutation is always detectable, matching the pattern the decision card's `role="alert"` region already gets right by construction (fresh distinct text each failure branch).
