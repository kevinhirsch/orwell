## Engine / ops
- **L18 ◐ ENG/OPS** — The engine **hangs and requires an FE reload** at `E22 guard: game turn narrated with no engine write - recording a fallback digest. process count = 2`, then 502s for a few seconds. Investigate the E22 fallback-digest path for the hang; determine if it is a specs/perf issue. **Update deploy defaults to recommend better container specs and document recommendations regardless.**

  **Diagnosis (2026-06-19).** Not a deadlock — a **latency/queue pileup**, worsened by an under-resourced host. The chain:
  1. The narration LLM **under-calls** the engine tools (the known gap the FE error-corrects). On every such turn the FE fires the E22 fallback `recordInteraction` **fire-and-forget** at stream `[DONE]` — `asyncio.create_task(ensure_turn_recorded(...))` in `frontend/routes/chat_routes.py` (~L1248), with no tracking. "`process count = 2`" is simply the FE's `_unrecorded_turn_fallbacks` counter reaching 2 (two under-called turns), **not** an OS process count.
  2. The engine **serializes all calls for one user** into a per-user promise queue (B60/audit E10, `src/adapters/mcp/HttpMcpServer.ts` `enqueue`). This is correct and must stay — it closes the sandbox-swap race. But it means the stacked fire-and-forget fallbacks **plus the next live turn's framing reads** all run strictly in order for that user.
  3. Each `recordInteraction` commit pays the **O(events) snapshot export + integrity checkpoint** (`registry.snapshot` → `exportSnapshot` runs `events.query()`; `Orchestrator.commitPlayerTurn` → `checkpoint` runs `toGameState`/`isSuperset` over the full event set; plus, in turn-driven mode, one off-screen tick with soul folds). The codebase already flags this as the unresolved **R3** cost ("late-season latency grows with the O(events) snapshot export"). On a 2 vCPU / 2 GB box (the old deploy default) several of these back-to-back, late season, blow past the FE's 30s engine timeout and the reverse-proxy window → the FE turn 502s and the UI looks hung until the queue drains. (The synchronous fastembed `Atomics.wait` embed bridge is **already** mitigated by the G8/G12 breathing lane — `recordToSoul` defers indexing one embed per macrotask — so soul writes are not the pin; `recall` is the only sync-embed-in-tool path and it is not used in any live tool.)

  **Fix shipped (safe, no game-logic / Vault-Wall change):**
  - **OPS / L18b** — raised the LXC deploy baseline to **4 vCPU / 8 GB RAM / 12 GB disk** (`deploy/orwell.sh` `CORES`/`RAM_MB`/`DISK_GB`; still env-overridable) and documented a **Recommended specs** section in `deploy/README.md` (LLM is remote ⇒ CPU is for FE + engine + local fastembed embeddings; more RAM if also running image generation).
  - **FE / L18a mitigation** — made the E22 fallback **single-flight per user** (`frontend/routes/chat_helpers.py` `ensure_turn_recorded` + `_fallback_in_flight`): a fallback fired while one is still committing for the same user is **skipped** (the under-call is still counted; the next real engine write or the next, now-unblocked fallback still records the consequence). This stops the fire-and-forget guard from stacking a backlog of O(events) commits behind the next live turn — the proximate trigger of the observed stall. Tests: `frontend/tests/test_lane6_turn_integrity.py` (concurrent same-user skip, per-user isolation, failure releases the slot).

  **Deferred (larger, not forced):** the **R3 incremental-snapshot** work — `exportSnapshot`/`checkpoint` are O(events) per mutation, so even with the single-flight guard and a bigger host, a very long season's per-turn commit cost keeps growing. The real cure is an append-only / incremental snapshot + checkpoint so a commit is O(Δ), not O(events). That is an engine-spine change (touches `src/composition/orchestrator.ts`, `registry.ts`, `sessionSnapshot.ts`) and should be its own queue item; it is intentionally **not** attempted here.
