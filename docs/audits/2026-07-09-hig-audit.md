# Apple HIG conformance audit — Orwell player front-end

**Date:** 2026-07-09 · **Scope:** `frontend/static/` (player-tier chat UI, HUD/gadget rail,
OrwellWindow/OrwellGadget kits, theme/glass system, settings). · **Type:** READ-ONLY audit.
**Epic:** [#694](https://github.com/kevinhirsch/orwell/issues/694) (per-guideline sub-issues
#695–#708). Companion backlog: [#738](https://github.com/kevinhirsch/orwell/issues/738)
(Liquid Glass fidelity).

This is a findings document only. **No code was changed.** Each finding is dispatchable as its
own fix PR; they are ranked so the overseer can pull the top items first. Every finding cites
`file:line`, states the HIG principle, and gives a concrete fix. Design language target: current
Apple (Liquid Glass, 2026) — so where the glass aesthetic and HIG legibility pull against each
other, the conflict is called out explicitly.

## 1. Accessibility & keyboard (HIG: Accessibility, Focus & selection)

### F-A11Y-1 · Live narration floods the `aria-live="polite"` transcript log — **P1**
- **Where:** `index.html:1243` — `<div id="chat-history" class="chat-history" role="log"
  aria-live="polite">`; streaming appends/mutates message bubbles *inside* this node
  (`js/chat.js:1205,2271–2314,2523,2779,2901` all target `#chat-history`).
- **What's wrong:** the narrator streams token-by-token deltas into bubbles that live inside a
  `polite` live region. A live region re-announces on **every** DOM mutation, so VoiceOver/NVDA
  will read partial, half-formed token fragments over and over as the reply streams — the
  transcript (which *is* the game, ADR 0003) becomes unusable with a screen reader.
- **HIG principle:** *Accessibility — "Support assistive technologies… announce content changes
  in a way that's useful, not overwhelming."* An actively-mutating stream must not be a live
  region.
- **Fix:** stream into a node with `aria-live="off"` (or outside any live region), and make **one**
  announcement per completed round — move the finished reply text into a small visually-hidden
  `aria-live="polite" aria-atomic="true"` announcer when the round closes (`agent_step`/round-end
  in `chat.js`). Keep `role="log"` on the container but drop the always-on `aria-live` from the
  streaming target. *(Needs a 1-line runtime confirmation with VoiceOver; the source pattern is
  the anti-pattern regardless.)*

### F-A11Y-2 · No "skip to content" link — keyboard/AT users tab the whole sidebar first — **P1**
- **Where:** first focusable content is the sidebar nav `index.html:939`
  (`<nav class="sidebar" id="sidebar" role="navigation">`); `<main id="chat-container">`
  (`index.html:1184`) and the composer come after it in DOM/focus order. No skip link exists
  (grep for `skip-link`/`skip-nav`/`skip to` finds only the *tour* skip button).
- **What's wrong:** every keyboard/switch/screen-reader user must Tab through the entire sidebar
  (sessions, tools, model picker…) on every load before reaching the chat composer — the one
  control they came for.
- **HIG principle:** *Accessibility / Keyboard — provide a way to bypass repeated blocks of
  navigation* (WCAG 2.4.1 Bypass Blocks).
- **Fix:** add a visually-hidden-until-focused skip link as the **first** child of `<body>`
  (`href="#chat-container"` or the composer id) reusing the existing `.a11y-visually-hidden`
  class (`style.css:12561`) with a `:focus-visible` reveal.

### F-A11Y-3 · Heading hierarchy skips levels + element-vs-ARIA mismatch — **P2**
- **Where:** `index.html:655,659,667,726,760,880` — `<h2 role="heading" aria-level="5">` (7
  occurrences); the only `<h1>` is visually hidden (`index.html:1189`). Settings panels also mix
  bare `<h2>` (no role) with these level-5 overrides.
- **What's wrong:** the document jumps `h1 → aria-level 5` with no 3/4 in between, and an `<h2>`
  element carrying `role="heading" aria-level="5"` is self-contradictory (native level 2 forced
  to 5). AT users navigating by heading get an illogical outline.
- **HIG principle:** *Typography / Accessibility — use a logical, consistent heading structure*
  (WCAG 1.3.1 Info & Relationships).
- **Fix:** use real nested elements (`<h2>`/`<h3>`) that reflect the true outline and delete the
  `role="heading" aria-level` overrides; if a visual size is wanted, style the real element.

### F-A11Y-4 · `title`-only affordances on icon controls don't reach touch/keyboard — **P3**
- **Where:** kit controls correctly carry `aria-label` (`orwellWindow.js:601,627,648,658`), but
  several titlebar/dock hints are `title=` only (`orwellWindow.js:614` "Drag to move · arrows to
  nudge"); `title` never surfaces on touch and is unreliable for AT.
- **What's wrong:** discoverability of keyboard-move / drag affordances is desktop-hover-only.
- **HIG principle:** *Accessibility — don't rely on hover-only cues.*
- **Fix:** where a `title` conveys the only instruction, mirror it into `aria-description`/an
  `aria-keyshortcuts` hint, or a one-time visible affordance. (Low urgency — the actions work; only
  their *discoverability* is hover-gated.)

## 2. Motion (HIG: Motion, Reduce Motion)

### F-MOTION-1 · Non-kit decorative animations lack a Reduce-Motion guard — **P2**
- **Where:** `.note-card-flash` (`style.css:37655`, a 1.6s box-shadow flash) has **no**
  `prefers-reduced-motion` guard; the `hwfit` schedule-chip transitions (`style.css:37601`) and
  other non-kit surfaces similarly. Reduce-Motion is applied thoroughly on the **kits** (`.ow-*`,
  `.og-*`, `.on-*`) and the animated background, but individual legacy/feature CSS animations opt
  in one-by-one, so new ones slip through.
- **What's wrong:** a Reduce-Motion user still gets flashes/transitions on these surfaces —
  inconsistent honoring of the OS setting.
- **HIG principle:** *Motion — "If a person has enabled Reduce Motion, replace or remove
  animations app-wide."* App-wide, not per-surface-opt-in.
- **Fix:** add a conservative global `@media (prefers-reduced-motion: reduce)` block that
  neutralizes decorative `animation`/`transition` on flash/pulse utility classes (scope it so it
  never touches functional state), **or** add a source-lint gate (mirroring the existing FE
  convention gates) that fails when a new `@keyframes`-driven class ships without a reduced-motion
  guard. The gate is the durable fix — it matches how the kits already stay compliant.

## 3. Legibility & contrast (HIG: Color, Materials — the glass↔legibility tension)

### F-CONTRAST-1 · `--fg-muted` secondary text over glass/photo backdrops risks the contrast floor — **P2**
- **Where:** `--fg-muted` (fallback `#888`) is used in **60+** places (`style.css:15300` and
  onward) for captions/secondary rows, including gadget rows and settings sub-labels rendered over
  the frosted/photo backdrop.
- **What's wrong:** muted grey at ~50–60% weight over a translucent glass surface laid over a
  wallpaper is exactly the "text-on-text / low-contrast over media" failure NN/g flags for Liquid
  Glass. The **AA/APCA floor is only proven for `.msg-ai` bubbles** (#1259); muted UI text on
  gadgets/settings is not yet under a floor. This is the surface-area that #738 item 19 (APCA
  increment) is meant to cover but hasn't yet.
- **HIG principle:** *Color / Materials — "Ensure sufficient contrast… don't place text where a
  material's translucency can drop it below a legible floor."*
- **Fix (rides #738 item 19):** extend the adaptiveGlass min-scrim contrast floor beyond `.msg-ai`
  to secondary-text surfaces over glass (gadget rows `.og-*`, settings sub-labels), or promote
  `--fg-muted` toward `--fg` when a glass tier is active. Assert in `browser_smoke`/the theme
  computed-style probe (`0114` gate, `#1247`) the way the bubble floor is asserted.

### F-CONTRAST-2 · Error state signalled by color alone — **P3**
- **Where:** `.hwfit-sched-err { color: var(--red) }` (`style.css:37641`); similar red-only error
  text elsewhere.
- **What's wrong:** red text is the sole error signal — invisible to color-blind users and low on
  glass.
- **HIG principle:** *Color — "Don't rely on color alone to communicate information"* (WCAG 1.4.1).
- **Fix:** pair error text with an icon/glyph and/or a leading "Error:" token; keep the red as
  reinforcement, not the only channel.

## 4. Touch targets & hit areas (HIG: layout for touch)

### F-TOUCH-1 · Kit titlebar controls are 32px on coarse pointers in the non-frosted theme — **P2**
- **Where:** `orwellWindow.js:292–294` — under `@media (pointer: coarse)` the `.ow-controls`
  buttons are floored at **32px**, not 44px, and they carry `.tap-exempt` to escape the global
  44px floor. The comment notes the **frosted** theme adds an invisible 44px `::after` hit region,
  but in the **legacy/non-frosted** path the actual hit box stays 32px.
- **What's wrong:** close/minimize/dock on a window are the highest-consequence controls (an
  accidental close loses the panel) yet fall below the 44pt target on touch in one theme — a
  deliberate but partial deviation.
- **HIG principle:** *Layout — "Provide ample touch targets… at least 44×44 pt."*
- **Fix:** extend the invisible ≥44px `::after` hit region (already used by the frosted disc) to
  the non-frosted `.ow-controls button` on coarse pointers, so the *visual* control stays a
  proportionate 32px but the *hit area* meets 44pt in both themes. This preserves the
  "no giant buttons dominating a 44px titlebar" intent while closing the gap. Pin it in
  `test_a8_mobile_window_kit.py`.

### F-TOUCH-2 · Gadget action buttons floor at 24px height — **P3**
- **Where:** `orwellGadget.js:88` — `.og-act { min-height: 24px }`; the coarse-pointer floor
  raises `[role=button]`/`button` but `.og-act` may inherit `.tap-exempt` patterns from the rail.
- **What's wrong:** "Open / Un-pin" gadget actions can present a sub-44 hit box on touch.
- **HIG principle:** *Layout — 44pt targets.*
- **Fix:** confirm `.og-act` is caught by the coarse-pointer floor (it should NOT be `.tap-exempt`
  unless a parent provides the hit area); if exempt, add the `::after` expansion as in F-TOUCH-1.

## 5. Safe areas & notch (HIG: layout, Devices)

### F-SAFE-1 · Landscape/left-right safe-area insets are essentially unused — **P2**
- **Where:** `--safe-left`/`--safe-right` are defined (`css/responsive-tokens.css:48–49`) but
  applied in only **one** place (`style.css:15552`, a floating corner); the sidebar/chat left edge
  and the composer don't consume the horizontal insets. Standalone padding applies `--safe-top`
  only (`responsive-tokens.css:92–95`).
- **What's wrong:** on a notched phone held in landscape (notch on the left), the sidebar/chat can
  slide under the sensor housing / rounded corner.
- **HIG principle:** *Layout — "Keep interactive and important content inside the safe area,"
  including the landscape sensor housing.*
- **Fix:** add `padding-left: max(<base>, var(--safe-left))` / `padding-right` to the outermost
  fixed chrome (sidebar, chat container, composer bar) so landscape insets are honored, matching
  how the bottom/home-indicator inset is already handled.

## 6. Control affordances & states; empty/loading/error (HIG: Components)

### F-STATE-1 · Disabled controls conveyed by opacity alone over glass — **P3**
- **Where:** `.email-send-btn:disabled { opacity: 0.5 }` (`style.css:30394`); frosted
  `.send-btn:disabled` / `.ow-window .ow-body button:disabled` (`style.css:38833–38836`).
- **What's wrong:** a 50%-opacity control over a translucent glass/photo backdrop can read as
  merely faint, not disabled; opacity-only disabling is ambiguous and can drop the label below the
  legibility floor.
- **HIG principle:** *Components / Buttons — a disabled control should be *clearly* non-interactive*
  (and remain distinguishable, not just dim).
- **Fix:** pair the opacity with `cursor: not-allowed` (present on `.email-send-btn`, absent on the
  frosted rule) and ensure `disabled`/`aria-disabled` is set in markup so AT announces state; keep
  the label above the contrast floor. Low urgency.

### F-STATE-2 · Loading affordance is solid; empty states are consistent — **NO ACTION (positive note)**
- The kit's non-blocking `.ow-loading` sliver + `·refreshing` hint (`orwellWindow.js:386–412`,
  reduced-motion aware) and the shared `.og-empty` treatment (`orwellGadget.js:102`) are exemplary
  HIG *Loading*/empty-state patterns. Called out so a fix PR does not "improve" them into
  blocking spinners.

## 7. Window chrome consistency & the glass↔HIG conflicts

### F-CHROME-1 · Two window families still coexist (kit `.ow-window` vs legacy `.modal-content`) — **P2**
- **Where:** kit `.ow-window` (26px radius, full chrome) vs legacy `.modal-content`
  (10px radius, `style.css:156`) still used by ~20 JS files (#738 item 27 / epic #660).
- **What's wrong:** two radii + two chrome builders mean windows/dialogs don't read as one system —
  the exact "unlearnable, inconsistent chrome" NN/g warns of. The a11y-trio and concentric-radius
  work is applied per-family, so a legacy modal can miss a treatment the kit has.
- **HIG principle:** *Components / Consistency — surfaces of the same kind should look and behave
  the same.*
- **Fix:** continue the #660 migration (legacy `.modal-content` → OrwellWindow kit). This is
  known/tracked; listed here so the HIG audit's window-consistency box is checked against it.

### F-CONFLICT-1 · System-blue focus ring vs "colorless glass chrome" — **resolved, documented**
- The mandate says glass chrome carries no accent HUE, yet focus rings are system-blue `#0a84ff`
  (`orwellWindow.js:256`, `orwellGadget.js:75`). This is the **correct** resolution: #729 sanctions
  system-blue as the one focus tint because **HIG focus visibility wins over the aesthetic** —
  a colorless focus ring on glass would be invisible. No change; recorded so a future "purge all
  accent color from chrome" pass does **not** strip the focus ring.

### F-CONFLICT-2 · Glass translucency vs legibility floor — the standing tension
- The whole Liquid Glass direction (translucent surfaces over an animated wallpaper) is in
  permanent tension with HIG *Color* contrast. It is **mostly** managed (a11y trio + `.msg-ai`
  floor), but F-CONTRAST-1 (muted UI text) is the live edge of it. Principle: **legibility is never
  load-bearing on glass** — every unresolved contrast question should resolve toward the tint/scrim
  floor, never toward more transparency. Flagged so future glass polish PRs keep that priority.
