## P0 — player-facing breakage / data loss

### G1. `frontend/gateway/handler.py:82` — silent-fail-soft / consequence-loop (mandate #4 — "never ship an action that is narrated but never recorded")

**Claim.** Every player turn taken through the live multi-platform gateway (feature 0072 — Telegram/Discord etc.) is narrated and delivered back to the player, but its hidden-layer consequence is never folded and never persisted, and — since only read-only engine tools are called — the orchestrator's per-turn off-screen tick never fires either. This is a silent, totally invisible bypass of the game's MVP-1 backbone for an entire shipped client surface.

**Evidence.** `_call_player_turn` (handler.py:82-146) calls only `orwell_engine.get_game_state` (read, line 102) and `orwell_engine.get_moment_prompt` (read, line 117), then makes one narration call via `_narrate_gateway_turn` (line 137) and returns the scrubbed reply (line 146). There is no call anywhere in gateway/ to `recordInteraction` or any other engine write-back tool (`grep -rn record_interaction gateway/` and `grep -rn recordInteraction gateway/` both return nothing). The docstring at handler.py:85-89 explicitly states the design 'avoids importing the full streaming agent loop' — that agent loop (`frontend/src/agent_loop.py`) is where the 0055 `_auto_record_scene` belt lives, the mechanism CLAUDE.md documents as the one guarantee that an engaged social turn folds its hidden impact even when the model itself skips the call ('the FE agent loop carries two in-loop guardrails ... GUARANTEEING the social play moves the hidden weights'). Because the gateway never imports agent_loop, that belt cannot fire either — there is no fallback of any kind. Since no engine write tool is ever called, `Orchestrator.commitPlayerTurn` (src/composition/orchestrator.ts:370) — the ONLY seam that fires the bounded off-screen tick keeping the house alive turn-to-turn — never runs for a gateway-only player, so the entire off-screen-society simulation is frozen for that channel too. Nothing logs this, and no RED-eligible event exists to surface it (no `record_soft_failure`/RED-recorder usage anywhere in gateway/). This is a live, wired path, not dead code: `frontend/routes/gateway_routes.py:35` imports `handle_platform_turn` and calls it at line 152, and `frontend/app.py:589-590` unconditionally mounts `setup_gateway_routes()` at boot.

**Verifier's confirmation.** Independently confirmed by direct code reading. frontend/gateway/handler.py:_call_player_turn (lines 82-146) calls only two read-only engine tools — orwell_engine.get_game_state (line 102) and orwell_engine.get_moment_prompt (line 117) — then makes a raw LLM call via _narrate_gateway_turn (line 137) and returns the reply; grep across frontend/gateway/ for record_interaction/recordInteraction returns zero hits, confirmed directly. On the engine side, GameSessionAdapter.getGameState/getMomentPrompt are pure reads (`return this.view()` / prompt-building off `this.view()`), and the orchestrator's off-screen tick is wired via `registry.setCommit(...) -> orchestrator.commitPlayerTurn(user)` (src/composition/runtime.ts:126), which fires only through the mutating-tool commit funnel — never on a read call. handler.py's own docstring confirms it deliberately does not import agent_loop.py (where the 0055 _auto_record_scene belt lives), so that fallback cannot fire either. The live-wiring claim also checks out: routes/gateway_routes.py imports and calls handle_platform_turn, and app.py mounts setup_gateway_routes() unconditionally at boot. Critically, this bug is newly "live": a NARR-1 fix (GitHub issue #620, closed 2026-07-11, visible in handler.py's own inline comment at lines 179-184) recently repaired an ImportError that had made the gateway's narration call always fail and return a placeholder — meaning before that fix this consequence-bypass was practically moot (nothing was ever really narrated), but now that narration genuinely fires, every real gateway turn is narrated with zero fold/persist/off-screen-tick. I searched the 0072 spec (docs/features/0072-multi-platform-gateway.md, which only frames skipping the agent loop as a narration-path simplification, never discusses the consequence-loop tradeoff), the 2026-07-21 campaign backlog doc (docs/audits/2026-07-21-campaign-report-and-exhaustive-backlog.md, fetched from origin/main since it isn't in this branch's tree — zero mentions of "gateway", "Telegram", "0072", or "multi-platform"), and GitHub issues (multiple queries: gateway, recordInteraction, NARR-1/2/3, consequence, off-screen tick) — the only related closed issues are NARR-1 (the now-fixed dead-narrator import), SEC-2/SEC-3 (webhook spoofing/rate-limiting), and unrelated NARR-7/9/10 narration bugs; none address this specific silent consequence/off-screen-tick bypass. It is not documented as intentional design anywhere. CLAUDE.md explicitly ranks this consequence/memory loop (feature 0023) as one of the four non-negotiable top priorities on par with the Vault Wall ("This is the point of the game... never ship an action that is narrated but never recorded"), and this gap silently defeats it for every turn on an entire live, wired, shipped client surface with no error, log, or RED-eligible signal to reveal it — matching the claimed P0 severity and failsoft-silent lens.

### G3. `frontend/app.py:462` — cross-user isolation fail-open (silent fail-soft on a security check)

**Claim.** The explicit cross-user ownership check for serving a player's/houseguest's generated image (0051 portraits) silently fails OPEN on any unexpected error instead of failing closed — contradicting its own inline 'SECURITY' comment and the project's stated cross-user isolation guarantee — with no log at any level and no RED-eligible event.

**Evidence.** `serve_generated_image` (app.py:439-479) reads: `try: ... _row = _db.query(_GI).filter(_GI.filename == filename).first(); if _row is not None and _row.owner and _row.owner != _user: raise HTTPException(404, ...) ... except HTTPException: raise / except Exception: pass` (lines 446-463). If `get_current_user`, `SessionLocal()`, or the ORM query raises for any reason (e.g. a SQLite lock/contention error, a schema hiccup) the code falls straight through the bare `except Exception: pass` and serves the image bytes regardless of ownership — the fail path is more permissive than the success path. Under AUTH_ENABLED=true (the multi-user, non-default-bypass configuration — `LOCALHOST_BYPASS` defaults false at app.py:187), `request.state.current_user` is guaranteed set by `AuthMiddleware` before this handler runs, so `_user` is truthy on essentially every real request, meaning the ownership branch is live, not dead code. Nothing is logged (no `logger.warning`/`error` call in the except block) and no RED-eligible recorder (`record_soft_failure` et al.) is reached, so this fail-open would leave zero trace in production even though CLAUDE.md calls cross-user isolation 'a first-class guarantee alongside the Vault Wall.'

**Verifier's confirmation.** Verified by direct read of frontend/app.py:439-479. The code exactly matches the claim: `serve_generated_image` does `_row = _db.query(_GI).filter(_GI.filename == filename).first()` then `if _row is not None and _row.owner and _row.owner != _user: raise HTTPException(404)`, wrapped by `except HTTPException: raise` followed by a bare `except Exception: pass` with zero logging. Any unexpected error while resolving ownership (SessionLocal() construction, the ORM query itself — e.g. a SQLite 'database is locked' contention error) is swallowed and execution falls through to serve the file bytes unconditionally — the failure path is MORE permissive than the success path, a textbook fail-open on a stated security control.

Checked all four refutation angles, none hold:
(1) Not dead code: get_current_user (src/auth_helpers.py) just reads request.state.current_user set by AuthMiddleware under AUTH_ENABLED=true, so `_user` is truthy on real authenticated requests — the ownership branch is live.
(2) Not documented/intentional: no ADR/CLAUDE.md passage sanctions this; the inline 'SECURITY' comment states the opposite intent. The SAME FILE's own convention for an adjacent security-critical except (app.py:394, bearer-token auth) is to log a warning AND fail closed (401) — directly contradicting the silent fail-open here. A `record_soft_failure` RED-style recorder (src/log_rings.py) exists and is used by many other modules for exactly this class of silent failure but is not invoked here.
(3) Not already tracked: the only existing audit hit on these lines is PERF-19 (docs/audits/2026-07-03-final-pre-ship-audit/lanes/performance.md), which flags the same code purely as a synchronous-DB-query performance concern (recommending a cache) — it never identifies the fail-open-on-exception security defect. No matching entry exists in the 2026-07-21 backlog doc either. New, untracked finding.
(4) Behavior confirmed directly from source, not speculation. No test in frontend/tests/ exercises this exception path.

Severity P1 (not P0): exploitation requires already knowing/guessing a 12-hex filename (an acknowledged pre-existing constraint) AND a transient exception firing on that specific request — not a permanently-open hole. But it's a real, silent violation of a guarantee CLAUDE.md calls first-class ("cross-user isolation... alongside the Vault Wall"), the triggering condition (DB contention on this exact hot path) is independently corroborated as realistic by the project's own PERF-19 finding, there is zero logging/telemetry to detect it, and no test covers it.
